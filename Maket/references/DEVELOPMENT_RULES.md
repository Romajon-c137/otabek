# Правила дальнейшей разработки

Навигация: [требования](TZ.md), [архитектура](ARCHITECTURE.md), [задачи](TASKS.md).
Текущий этап — начало реализации. Веб-макет остаётся неизменяемым эталоном; production-код создаётся отдельно в `backend/` и `client/`.

1. Начать следующую сессию с TASKS.md: TASK-001 и TASK-002 завершены, TASK-004 находится в работе; прочитать требования, решения и зависимости. Документирование эталона TASK-003 допускается параллельно.
2. Решения Q-001…Q-007 зафиксированы в `TZ.md`. Изменять их можно только явно, одновременно обновляя требования, архитектуру, задачи и проверки. Блокировка отдельной задачи не блокирует независимые работы.
3. Перевести задачу в IN_PROGRESS, описать конкретный объём; не менять соседние сценарии и утверждённые экраны без основания. На текущем этапе все задачи реализации TODO.
4. Проверять деньги, количества, остатки, резерв, полномочия и зависимости на backend. UI — средство ввода, не учётная система. Режим «администратор» не заменяет авторизацию.
5. Писать отдельные прикладные сценарии; HTTP-обработчик не содержит бизнес-процесс. Изменять остатки и расчёты только движениями штатных сервисов. Не править balance вручную.
6. Связанные записи изменять атомарно, с единым порядком блокировок и идемпотентностью. Не проверять остаток только до транзакции. Конкурентные тесты выполняются на PostgreSQL с разными соединениями.
7. Проведённые документы/движения неизменяемы. Исправление через сторно и новый документ, с автором, причиной и зависимостями. Не удалять реальные данные, файлы и миграции без анализа и восстановимой копии.
8. Для очистки: инвентаризация → список кандидатов → проверка ссылок → архив → проверка запуска. Seed/localStorage остаются в демо до приёмки нового клиента. Сохранить историю старых ТЗ.
9. На каждую бизнес-задачу добавить её сценарии приёмки и ошибки из TASKS.md. Проверить существующие затронутые сценарии; не подменять тест двух клиентов последовательным вызовом одного объекта. 20 JS проверок — примеры для переноса, не доказательство работы сервера.
10. Для C# экранов проверить клавиатуру, фокус, переподключение, конфликт версии и повтор после timeout; сохранить введённые строки при ошибке. Сравнивать с эталоном, не добавлять тестовые тексты в рабочие формы.
11. Обновлять связанные REQ/TASK/API при изменении решений. Не менять нумерацию существующих ID; новые получают новые номера. В TASKS вести дату, доказательство проверки и ссылку на изменения.
12. DONE только после всех критериев, выполнения зависимостей и успешной проверки. При BLOCKED записать причину, нужное решение/доступ и следующую независимую работу. Нельзя ставить DONE только потому, что написан код.
13. Итог каждого шага: что изменено; как проверено (команда/результат/ограничения); какая задача следующая. Перед рабочим запуском подтвердить restore, права, отсутствие отрицательных остатков и сверку истории.

## Контроль документации

Каждый REQ имеет задачи в матрице TASKS.md; каждая задача имеет цель, приоритет, зависимости, шаги, правила, приёмку, проверку и статус. Зависимости должны идти к более ранним задачам. Неизвестное оформляется вопросом с задачей решения, а не пустым «позже». При конфликте старых документов использовать приоритет TZ.md и явно фиксировать изменение.
