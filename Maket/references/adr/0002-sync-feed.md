# ADR-0002: Лента изменений и этапы заказа

Статус: принято 08.10.2026.

Контекст: несколько Windows-касс работают с общим сервером. Продажа выполняется в кассе (из заказа или напрямую). Касса должна сразу видеть изменения других пользователей и работать мгновенно. Единственный источник истины — сервер (PostgreSQL); клиенты держат локальную копию.

Решение:

- Сервер ведёт ленту `ChangeEvent`: каждое изменение документа, заказа, товара или контрагента получает номер `seq`. Номера выдаются после фиксации транзакции под блокировкой строки `SyncCounter`, поэтому порядок строгий и откат не публикует событие.
- `GET /api/v1/sync/state/` — текущий номер. Клиент берёт его до загрузки снимка данных.
- `GET /api/v1/sync/changes/?since=N&limit=500&wait=25` — события после `N`. При `wait>0` запрос ждёт новое событие до указанного времени (long polling). Курсор `last_seq` продвигается и через события чужих складов.
- Событие — это сигнал «сущность изменилась» с краткими полями (тип, номер, статус, контрагент, автор); полные данные клиент получает обычным API.
- Long polling выбран вместо WebSocket: не нужен Redis и Channels, переживает обрывы связи, задержка доставки не больше 0,5 секунды. WebSocket можно добавить позже, сохранив ту же ленту.
- Этапы заказа: `draft` «Новый» → `reserved` «Собираем» → (`assembled` «Собран») → `shipped` «Отправлен» → `completed` «Доставлен». Переходы `ship`/`unship`; отправленный заказ сохраняет резерв, его можно продать или отменить.

Последствия: клиенты обязаны хранить свой курсор и при запуске догружать пропущенные события. Продажа без связи допустима в кассе; возможны конфликты между несколькими кассами. Хранение ленты без очистки; очистку старых событий решить при эксплуатации.
