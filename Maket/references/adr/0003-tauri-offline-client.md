# ADR-0003: Программа на Tauri, локальная копия и очередь отправки

Статус: принято 09.10.2026. Заменяет ADR-0001 (WPF) для новой программы; WPF-клиент остаётся в репозитории как неподдерживаемый прототип.

Контекст: нужна Windows-программа, работающая мгновенно и синхронизирующая данные с общим сервером. Интерфейс утверждён в веб-макете. Продажи, заказы и приходы оформляются в кассе.

Решение:

- Клиент — Tauri 2 (Rust + WebView2). Интерфейс — те же `index.html`, `css/`, `js/`, что в макете; сборка `tools/build-web.mjs` копирует их в `app/web`.
- Источник истины — сервер (Django + PostgreSQL). Касса держит локальную копию (IndexedDB: проекция данных, очередь отправки, курсор ленты).
- Действие сначала выполняется локально тем же движком `js/engine.js` и сразу ставится в очередь; очередь уходит на сервер по порядку. Идентификаторы документов (UUID) и `Idempotency-Key` выдаёт клиент, поэтому повтор после обрыва безопасен.
- Номера документов назначает сервер (`ПР-000001`); до отправки в кассе показывается временный номер `ПР~3`.
- Ошибка сервера (например, не хватило товара) — не повторяется: операция попадает в список «не отправлено», локальная копия обновляется данными сервера.
- Новое с других устройств приходит через ленту изменений `/sync/changes` (long polling); при непустой очереди обновление копии откладывается до её опустошения.
- Вход по токену (`/auth/token/`), пароль на устройстве не хранится. Запросы из программы разрешаются через `CORS_ALLOWED_ORIGINS` (для Windows: `http://tauri.localhost`).
- Администрирование (товары, отчёты, импорт) в рабочем режиме пока не подключено: в демо оно работает на локальных данных.

Последствия: два движка расчёта (клиентский для мгновенного ответа и серверный авторитетный) должны давать одинаковый результат; расхождения ловятся тестами `tests/engine.test.js` и `apps/*/tests*.py`. Возврат товаром и взаимозачёт «вручную» пока только на сервере.
